# 会话管理模块 技术实施方案

## 背景

需求来源：`.agent/2.会话管理模块创建/需求文档.md`。目标为服务端实现会话管理 RESTful 接口（新建、列表、删除、获取历史消息），数据持久化到 MySQL，所有接口需鉴权。

当前状态：项目使用 SQLite + 内存存储，无 ORM 模型定义。本次需引入 MySQL 作为服务层数据库，创建首批 SQLAlchemy 模型，并实现完整的会话 CRUD + 消息查询。

## 方案设计

### 整体思路

1. **双数据库架构**：服务层使用 MySQL（aiomysql 异步驱动），agent 层保留 SQLite。通过两个独立的 engine/session 实现隔离。
2. **ORM 模型**：创建 `Conversation` 和 `Message` 两个 SQLAlchemy 模型，一对多关系，硬删除级联。
3. **Schema 层**：新增会话相关 Pydantic 模型（ConversationCreate/ConversationOut/ConversationDetailOut），调整 MessageOut 增加 conversation_id。
4. **Service 层**：新建 ConversationService，重构 MessageService 从内存迁移到 MySQL ORM。
5. **API 层**：新增 `/conversation` 路由，4 个接口全部鉴权。

### 关键技术选型

| 项 | 选型 | 说明 |
|---|---|---|
| MySQL 驱动 | aiomysql | 异步驱动，与现有 async 架构一致 |
| ORM | SQLAlchemy 2.0 async | 项目已引入，沿用声明式模型 |
| thread_id 生成 | uuid4 | 服务端自动生成，关联 agent 记忆 |
| 删除策略 | CASCADE 硬删除 | 删除会话时级联删除关联消息 |

### 数据结构

**Conversation 表**：

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT | PK, AUTO_INCREMENT | 主键 |
| thread_id | VARCHAR(36) | UNIQUE, NOT NULL | 会话记忆关联 ID (UUID) |
| user_id | BIGINT | NOT NULL, INDEX | 所属用户 ID |
| title | VARCHAR(200) | NOT NULL, DEFAULT '新会话' | 会话标题 |
| created_at | DATETIME | NOT NULL | 创建时间 |
| updated_at | DATETIME | NOT NULL | 更新时间 |

**Message 表**：

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT | PK, AUTO_INCREMENT | 主键 |
| conversation_id | BIGINT | FK → conversation.id, ON DELETE CASCADE, INDEX | 所属会话 |
| user_id | BIGINT | NOT NULL, INDEX | 发送者用户 ID |
| role | VARCHAR(20) | NOT NULL, DEFAULT 'user' | 消息角色 (user/assistant/system) |
| content | TEXT | NOT NULL | 消息内容 |
| created_at | DATETIME | NOT NULL | 创建时间 |

### 接口定义

| Method | Path | 说明 | 鉴权 |
|--------|------|------|------|
| POST | `/api/v1/conversation` | 新建会话 | Yes |
| GET | `/api/v1/conversation` | 获取当前用户会话列表 | Yes |
| DELETE | `/api/v1/conversation/{id}` | 删除会话（级联删除消息） | Yes |
| GET | `/api/v1/conversation/{id}/messages` | 获取会话历史消息 | Yes |

## 实施步骤

1. **数据库配置与连接** — 修改 config.py、database.py、.env，新增 MySQL 连接
   - 与后续步骤：串行（后续步骤依赖数据库连接）

2. **ORM 模型** — 创建 Conversation、Message 模型，更新 models/__init__.py
   - 与步骤1：串行

3. **Schema 层** — 新增 conversation schema，调整 message schema
   - 与步骤2：并行（schema 和 model 无代码依赖）

4. **Service 层** — 新建 ConversationService，重构 MessageService
   - 与步骤2、3：串行（依赖 model 和 schema）

5. **API 路由层** — 新增 conversation 路由，调整 message 路由，注册到 router
   - 与步骤4：串行（依赖 service）

6. **启动验证** — 确认 MySQL 表自动创建，接口可正常调用
   - 与步骤5：串行

## 风险与注意

- **MySQL 连接**：需确保 192.168.1.19 MySQL 服务可访问，wedding 数据库已创建，aiomysql 已安装
- **数据迁移**：MessageService 从内存迁移到 MySQL，现有内存数据将丢失（当前为开发阶段，可接受）
- **双数据库**：lifespan 中需同时初始化 MySQL 和 SQLite 的表创建，注意区分 engine
- **外键级联**：MySQL 需确保 InnoDB 引擎（支持外键），CASCADE 删除需测试验证
